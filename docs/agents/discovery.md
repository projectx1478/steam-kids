# 発見フェーズ（問診＋Web調査→提案カード）

新機能・改善の方向を決める前に読む（Claude Codeの入口は`/discover <テーマ>`）。上位ティアで実行し、コードは変更しない。成果物は提案カードとIssueだけ。依頼文に無い望みを引き出し、想定を超える案を根拠つきで出すのが目的。手順1→5を順に行い、飛ばさない。

## 手順1：下調べ（質問の前に必ず）

`PROJECT.md`、関連Issue（オープン、直近のクローズ済み、「見送り」の記録）、該当画面のコードを読む。ファイルを読めば分かることは質問しない。分かったことを3行で示してから問診に入る。

## 手順2：問診（最大3往復・1往復4問まで）

選択肢つきの質問で聞く（Claude CodeではAskUserQuestion。無いツールは番号つき選択肢）。次の6種から、下調べで埋まらなかったものだけを選ぶ。

| 種類 | 例 |
|---|---|
| 目的 | これができたら、次に何をしたくなりますか |
| 場面 | いつ・どの端末で・何分くらいで使いますか |
| 痛点 | 今いちばん面倒な瞬間、やめてしまう瞬間はどこですか |
| 理想 | 手間ゼロなら、どうなっていてほしいですか |
| 制約 | 費用・個人情報・速さのうち、譲れないのはどれですか |
| 対象外 | やらないと決めていることはありますか |

- 選択肢は下調べから作った具体的なもの（実在の画面名・場面）にする。一般論の選択肢は答えても何も決まらない
- 各質問に「おまかせ（推奨を採用）」を必ず入れ、推奨がどれかを示す
- 各選択肢の説明には、それを選んだら画面で何が起きるかを1文で書く（押す→見える→結果）。選ぶ過程そのものが想像を広げる
- 2往復目は「方向の感触」を聞く。1往復目の回答から作った具体的な方向を3つ示し、惹かれるもの（複数可）と、惹かれない理由を選んでもらう。カードの種になる
- 3往復目は、2往復目の回答で初めて生じた分岐だけを聞く。無ければ行わない
- 開発者が「もう十分」と言ったら、残りの往復を省いて先へ進む
- 回答はテーマのIssueに「問診の記録」（質問と回答を1行ずつ）として残す。別セッション・別モデルが再質問しないため。テーマのIssueが無ければ、問診の後に下調べ・問診の記録を本文にして作る（問診前に中身の薄いIssueを作らない）

## 手順3：Web調査（上限つき）

- 上限は検索6回・ページ閲覧4件。達したら、足りなくても打ち切って手順4へ進む
- サブエージェントに任せ、400字以内の要約と出典URLだけを受け取る（無いツールはメインで行い要約だけ残す）。同じ調査を2回頼まない
- 観点は次の4つから、テーマに合う2つ以上：同種の製品の定番と評価の高い点／利用者の不満（レビュー・掲示板）／使える技術（ブラウザ機能・無料API・ライブラリ）／デザインの型
- **検索語にプロジェクト名・利用者名・個人情報・非公開の内容を入れない。** 一般的な語だけで検索する（「日記アプリ 続かない 理由」は可、リポジトリ名や問診の回答文そのものは不可）。サブエージェントへの依頼文にもこの規則を書く
- 依頼文は絞る：調べる問いは3つまで、背景は3行まで、ページ閲覧が失敗したら別のページで再試行しない（調査だけで実装1件分の0.3を超えないため）
- ページを閲覧できなかったとき（ネットワーク制限等）は、根拠が検索結果の要約文だけであることを、要約・提案カード・Issueに明記する。未確認の受け口は、起票するIssueの「設計時に最初に確かめること」に書く
- 出典の無い主張は根拠にしない。見つからなかったことは「見つからなかった」と書く

## 手順4：提案カード（5〜7枚）

```
### <名前>
- 嬉しいこと：<1文>
- 場面：<使う場面を3〜4文で。いつ・どこで、何を押し、何が見え、どうなるかの順>
- 画面：<ボタン名・表示される文言の例を1行>
- 根拠：<問診の回答、または出典URL>
- 規模：S／M／L
- リスク：<やらない理由になりうる点>
```

- 場面と画面は、そのプロジェクトの実在の画面名・ボタン名・問診で出た状況を使って書く（読んだ人が自分の端末での操作を思い浮かべられること）
- 大胆案を必ず1枚（採用されなくてよい。想像の幅を広げる役）。依頼の延長ではなく、問診の「目的」「理想」から逆算して作る
- 「やらない方がよい」を必ず1枚（調査で分かった、手を出すと損をするもの）
- 推奨の順に並べ、上位3枚に推奨の理由を1行
- 根拠が書けないカードは出さない
- 絵・モックは作らない（費用のため）。`variants`ラベル付きIssueの設計時だけ作る（`docs/agents/dev-flow.md`）
- 規模：S＝1〜3ファイル／M＝設計1回・実装1セッション／L＝段に分ける

## 手順5：選ばれたカードをIssueにする

- 選ばれたカードだけ起票する（1カード＝1 Issue、ラベル`needs-design`）。本文にカードの全文と関係する問診の回答を写す（設計役がテーマのIssueを読み直さずに済む）
- 選ばれなかったカードは、テーマのIssueに「見送り」として1行ずつ残す（名前＋理由。同じ提案の繰り返しを防ぐ）
- 起票したら終了。設計は別セッションで行う

## 費用の目安

1テーマあたり、中規模Issueの実装1件の0.3〜0.5。超えそうなら、先にテーマを狭めることを提案する。
