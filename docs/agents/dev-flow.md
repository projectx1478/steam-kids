# 設計→実装の軽量フロー

Issueの設計、または`ready`のIssueの実装を始めるときに読む（Claude Codeの入口は`/design <N>`・`/implement <N>`）。AGENTS.mdの規則はそのまま有効で、本書は状態と手順を足す。

## 状態（Issueラベル）

`needs-design` → `needs-decision`（判断待ち）→ `ready`（承認済み）→ `agent:<tool>`（着手中）

- `ready`は人が付ける。チャットで「#N 承認」と言われたらAIが付けてよい
- 状態ファイルは作らない。設計の正本はIssue本文（コメントで確定した変更は本文へ反映する）
- 1 Issue＝1セッション。Issueを読めば始められる状態にしてセッションを閉じ、長いセッションを引き継がない（文脈が長いほど毎ターンの消費が増える）

## 設計（上位ティア。コードは変更しない）

1. Issue本文とコメントを読み、対象ファイルを読んでgrepする
2. `.github/ISSUE_TEMPLATE/design.md`の見出しでIssue本文を書き直す。該当なしの見出しは「なし」と書き、消さない
3. `判断が必要な点`が残れば`needs-decision`を付けて聞く。無ければ承認を求める。`needs-design`は外す

書き方の基準：

- 実装役が1つも質問せずに書ける。id・文言・数値を本文に書く（「適切な」を残さない）
- `受け入れ条件`は機械で確かめられる形（数値・セレクタ・関数の入出力）
- 変えないものを明記する
- `区分`はS（1〜3ファイル）かM（1セッションで終わる）。超えるなら段ごとのIssueに割る

## 実装（実装ティア）

事前確認：`ready`あり／依存先クローズ済み／`agent:*`なし。1つでも欠ければ実装せず報告する。

1. `agent:<tool>`を付け、`origin/main`起点でブランチを切る
2. 純粋関数の`受け入れ条件`は、実装より先にテストを書く（条件をそのまま写す）
3. 実装する。設計に無い変更はしない。読むのは`実装場所・影響範囲`のファイルだけ
4. 軽量チェックを手元で実行する（PROJECT.md「検証コマンド」）
5. 自己点検：`docs/checklist.md`があれば従う。無ければ共通5項目＝範囲外の変更なし（`git diff --stat`で確認）／配布ファイルを変えていない／テストを弱めていない／秘密情報なし／文書を更新した
6. 下書きPRを作り、CIの結果を確認して報告する

打ち切り：同じ失敗が修正2回で直らない／設計に無い判断が出た。どちらかで止まり、`needs-decision`を付けて分かったことと選択肢をIssueにコメントする。推測で進めない。

続けて進める：`/implement next`は、`ready`かつ依存先がすべてクローズ済みのIssueを番号の若い順に1件選ぶ。`next 2`で最大2件（上限。続けるほど文脈が膨らむ）。PRは1件ごとに分け、1件目が打ち切りなら2件目へ進まない。

## 報告（振り返りの輪）

AGENTS.md「報告形式」に加え、「設計に無かった判断」「CI・自己点検で見つかった不具合」を必ず書く（無ければ「なし」）。それぞれを設計の型・`docs/pitfalls.md`・テストのどれかに1行で戻す。配布ファイルへ戻す場合は自分で変えず、テンプレート元のIssueにする。

PR本文に、呼んだオプションと修正回数を1行で書く（例：`オプション：なし／修正：CI後1回`。費用の実測）。

## オプション（既定OFF）

Issueにラベルが付いたときだけ行う。自分の判断では呼ばない。上乗せは中規模Issueの実装1件を1とした目安。

| ラベル | すること | 上乗せ |
|---|---|---|
| `variants` | 設計時に「堅実／推奨／大胆」の3案を実画面の撮影で並べる | +0.5〜1 |
| `review:upper` | マージ前に上位ティアの審査役（読み取りのみ）を呼ぶ | +0.3〜0.5 |
| `check:separate` | 実装と別の文脈の照合役が、設計と差分を照らす | +0.2〜0.3 |

- Claude Codeでは審査役＝`.claude/agents/flow-reviewer.md`、照合役＝`flow-checker.md`。サブエージェントが無いツールは、別セッションでPR差分とIssue本文だけを読んで行う
- `review:upper`を勧める場面：認証・課金・個人情報・データ移行・外部APIの契約に触れるPR。設計時に`判断が必要な点`へ書く

## トークン節約

- 画面の確認は、画像を読まず寸法・文字列の数値検査で行う。撮影は人が見る用
- 調査・ログ取得はサブエージェントに任せ、要約だけ受け取る。起動のたびに読み直すため、同じ調査を2回頼まない

## リポジトリが自分で持つもの（配布しない）

- `docs/checklist.md`：そのリポジトリ固有の点検表（過去の失敗から）
- `docs/pitfalls.md`：落とし穴集（1件1行：症状／原因／見分け方／出典Issue。上限4,000字）

ひな形は`.claude/templates/`。
