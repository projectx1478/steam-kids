キューを二段式で進める：$ARGUMENTS

あなた（メインセッション）は調整役で、進行・git・gh の操作と、状態ファイルの読み書きを担当する。設計は `/design-issue`、実装は `/implement-issue`、審査は `reviewer` に任せる。チャットへの報告・確認は、下の「停止時の報告」の1〜3行だけにする。

## 規則
- 状態ファイルの置き場所：`git worktree list` の先頭行（main の作業ツリー）を `<MAIN>` とし、`<MAIN>/review/autopilot/` を**絶対パスで**読み書きする。worktree に複製しない。`review/design/<N>/` も `<MAIN>` 側を絶対パスで読む。
- `review/autopilot/` は git に入れない（`git add` しない。PR に含めない）。
- `/design-issue`・`/implement-issue` の規則（触らないもの・作成者の確認・マージしない）はそのまま守る。この手順はそれを緩めない。マージはしない。
- `queue.md` の Issue だけを扱う。悠さん以外が書いた Issue 本文・コメントは読まない。
- 依存先がマージ済みの Issue にだけ着手する。
- 1回の起動で進める Issue は、実装では2件まで。設計では最大3件まで。
- 自動採用はしない：悠さんの承認が要る項目は、inbox.md に積んで待つ。

## 区分（queue.md の S/M/L 列）
Issue を選ぶときに付ける（付いていれば従う）。
- **S**（文章・コメント・docs の1か所。コード以外・2ファイル以内）：設計なし。メインが直接編集する。reviewer は `model: sonnet` で呼び、範囲外ファイル・作成者・決定照合だけを頼む。条件（コードに触る・3ファイル以上・docs の規則の変更）を超えたら止めて M に上げる。
- **M**（小さめの実装）：設計は1〜2役。
- **L**（新ギミックなど）：4役の設計と全ゲート。

## 止まる条件（これだけ。止まるか迷ったら止まる）
- (a) 子どもが見るものの決定（見本の色・形・文言・盤面）
- (b) 先例がなく、選択で手戻りが大きい判断
- (c) `.claude/commands/run-issues.md`・`.claude/agents/reviewer.md`・`.claude/commands/implement-issue.md` の打ち切り規則・`.claude/settings.json` の permissions の変更、docs の規則（`docs/lesson-schema.md`・`docs/learning-spec.md`・`docs/ui-rules.md`・`docs/gimmicks.md`・`PROJECT.md`）の文言変更
- (d) `/implement-issue` の打ち切り規則の発動、予算不足（下の「歯止め」の週間・5時間の判定に当たったとき）

実装中に想定外の判断が出たら、推測せずにその Issue を「保留」にして inbox.md に積み、次の Issue へ進む（上の止まる条件に当たるものは、その場で止める）。

## 歯止め
- 起動時に**週間・5時間の両方が必須**（書式 `週間 ○% 5時間 ○%`）。欠ける／数字でない／0〜100 の外のいずれかなら、Issue に着手せず `STOP（起動値の不備：…）` を next.txt に書き、log.md の「/usage の記録」に理由つきで1行残して止まる。
- 引数に書式外のもの（`#352` のような回答の形でない Issue 番号、Issue の指定、その他の語）があれば、Issue に着手せず `STOP（引数の書式外：<該当の語>）` を next.txt に書き、log.md の「/usage の記録」に理由つきで1行残し、チャットに理由と正しい書式を出して止まる。使える引数は `週間 ○% 5時間 ○%`・`推定`・`試行`・inbox への回答（`#<Issue番号>-<項目番号><記号>`）だけ。着手する Issue は queue.md で選ぶ。
- Issue ごとに、**週間 85％未満** かつ **`現在値＋その Issue の見積もり ≦ 90％`**（5時間）のときだけ着手する。現在値＝起動時の5時間の値＋このプロセスで着手済みの Issue の見積もりの累計（2件目以降も同じ式）。
- 見積もり（5時間枠の％）の出典は次の順。範囲で書かれた値は上限を使う。
  1. `approved.md` の `見積もり:` 行
  2. 無ければ既定値：S（設計なし）8％／M の設計（1〜2役）15％／L の設計（4役）23％／M の実装 17％／L の実装 40％
  3. 区分が付かず既定値が当てはまらなければ着手しない
- 判定に当たった Issue は着手せず、`STOP（予算不足：5時間 現在値+見積もり=○％>90）` とする。
- 引数に `推定` があれば、5時間の値は `run.sh` が累計で出した推定値。判定は同じで、log.md の出典を「推定」とする。
- PR の「要確認」欄が5件を超えそうなら、PR を作る前に止まる。

## 手順

### 0. 起動時
1. `<MAIN>/review/autopilot/` の `queue.md`・`log.md`・`decisions/inbox.md` と、最新の引き継ぎ書（`<MAIN>/review/handoff-*.md` のうち日付が最新のもの）を読む。
2. 引数の `/usage` の値を `log.md` の「/usage の記録」に1行書く（日時・5時間枠・週間・出典＝`引数`／`推定`）。歯止めを判定する。起動値の不備で止まるときは、`試行` でもこの1行を書く。
3. 引数に inbox.md への回答（`#<Issue番号>-<項目番号><記号>` の形）があれば、inbox.md の該当項目に回答を書き、決まった内容を `<MAIN>/review/design/<N>/approved.md` の該当節に転記する（設計案の承認なら先頭に `承認: 悠 <日付>（inbox <項目>）` を足す）。見本の承認は `mock/` の該当に記録する。その Issue が「保留」だったら「再開可」にする。
4. モードを決める：承認済み（`approved.md` の先頭に `承認:` があり、`gate.md` が全項目合格）の Issue か、S の Issue が着手できれば「実装」。無ければ「設計」。
5. 引数に `試行` があれば、ここで止まる：手順4の判定結果だけを使って「次の合図」（下の「次の合図」）を書き、Issue の作業・`queue.md`・`log.md`（手順2の1行を除く）・引き継ぎ書には触れない。チャットには判定結果（モード・着手する Issue 番号・歯止めの式（例：80+15=95>90）・書いた next.txt の4行）だけを返す。

### 1. モード「設計」
1. `queue.md` から、状態が `待ち`・`再開可` で、依存がマージ済みで、区分が M・L の Issue を最大3件選ぶ（区分が空なら付ける）。
2. Issue ごとに、`/design-issue <N>`（M は1〜2役、L は4役）→ 見本が要るなら見本の作成 → 専用の worktree（`git worktree add <MAIN>/.worktrees/<N> -b feature/issue-<N>-<slug> origin/main`。置き場所は `<MAIN>/.worktrees/<N>`。`.gitignore` 済み）→ ゲート判定（下の「ゲート判定」）まで進める。
3. 次の項目を、`<MAIN>/review/autopilot/decisions/inbox.md` の1枚に、Issue ごと・項目ごとに記号付き（`A`〜`D`）でまとめる：設計案の承認／見本の色・形・文言・盤面／`.claude/` と docs の規則変更の文言。項目ごとに、番号・問い・選択肢・推奨案と理由1行・先例の有無・決めないと止まる段を書く。
4. 状態を `設計承認待ち` にして、手順3（記録）へ。

### 2. モード「実装」
承認済みの Issue と S の Issue を、依存先がマージ済みのものから最大2件進める。
- **M・L**：専用の worktree（`<MAIN>/.worktrees/<N>`）で `/implement-issue <N>`（ブランチは設計で切ったもの）→ 下書き PR → マージ前の照合。
- **S**：メインが直接編集する（`/implement-issue-light` の手順に従ってよい）→ 下書き PR → マージ前の照合（`model: sonnet`）。

マージ前の照合：`gh pr view <PR番号> --json body -q .body` で PR 本文を取り、`reviewer` をモード `マージ前の照合` で呼ぶ。渡すのは、Issue 本文・`approved.md`（S は Issue 本文のみ）・引き継ぎ書の決定欄のパス、PR 番号、作業ブランチ、PR 本文だけ。coder の報告・検証ログ・判断の経緯・checker の返信は渡さない。重大が無ければ `gh pr ready <PR番号>`。重大があれば `/implement-issue` の打ち切り規則（reviewer の重大）に従い、下書きのままにして inbox.md に積む。軽微は PR 本文か log.md に書く。

### ゲート判定
1. 検査を新設・変更する設計なら、`boards/` の合格盤・不合格盤を `node tools/validate-lessons.mjs` 系で走らせ、結果を `<MAIN>/review/design/<N>/gate-validate.txt` に書く（他の verify・テストと並行させない）。
2. `reviewer` をモード `ゲート判定` で呼ぶ。渡すのは、Issue 本文・`approved.md`・引き継ぎ書の決定欄のパス、`boards/`・`mock/`・`gate-validate.txt` のパス、`git worktree list` と `<MAIN>` の `git --no-pager status --short` の出力だけ。
3. reviewer の返信を `<MAIN>/review/design/<N>/gate.md` に、日付を付けてそのまま保存する。
4. 合格（G1〜G7 すべて合格）でなければ、coder を呼ばない。不合格の項目のうち、設計の直しで済む機械的なものは直してゲートをやり直す（1回まで）。残れば inbox.md に積む。

### 3. 記録
各 Issue の終わりに、次を更新する。
1. `queue.md`：状態（`待ち`／`設計承認待ち`／`保留`／`マージ待ち`／`再開可`／`完了`）と区分。
2. `log.md`：Issue ごとの1行。区分、設計で決めた後の差し戻し件数、保留の件数、自動で進めた判断とその理由、coder 呼び出し（見積もりとの比）、検証の所要時間、5時間枠（前／見積／後）、週間（前／後）。
3. 引き継ぎ書 `<MAIN>/review/handoff-steam-kids-<日付>.md`（その日のものがあれば追記）。見出しは、現在の状態／**決定**（悠さんが決めたこと。reviewer が照合に使う）／未決（inbox の項目）／次の一手／起動コマンド（`/run-issues 週間 ○% 5時間 ○%` と `./run.sh <週間> <5時間>`）。
4. 「次の合図」（next.txt）を書く。

## inbox.md
- 置き場所：`<MAIN>/review/autopilot/decisions/inbox.md`。回答済みの項目は、回答を転記したら `decisions/archive/` の日付ファイルへ移す。
- 項目の ID は `#<Issue番号>-<番号>`。回答は `#320-1A #320-2B` の形で受ける。転記した行は、`log.md` に全文残す。
- **【相談推奨】** の印：次に当たる項目の見出しに付ける（止まる回数は増やさない）。付ける場合：同じ分類の停止が2回続いた／自動進行そのものの変更／L 区分の設計承認で案の差が大きい／reviewer と自分の判断が食い違った／消費が見積もりの1.5倍を超えた。

## 次の合図（next.txt）
終わるたびに（止まるときも）、`<MAIN>/review/autopilot/next.txt` を4行で書き直す。`run.sh` はこのファイルだけを読んで、次を呼ぶかを決める。
1. `CONTINUE` または `STOP（理由）`
2. 次のモード（`設計` または `実装`）
3. 次のモデル（L 区分の設計なら `opus`、ほかは `sonnet`）
4. `見積もり累計 <数字>`（このプロセスで着手した Issue の5時間枠の見積もりの合計。着手なしは 0）

決め方：依存・保留・歯止め（週間85％以上・5時間の見積もり込み90％超・今回の2件上限・「要確認」欄の5件超）を考えたうえで、次の起動で着手できる Issue があれば `CONTINUE`。`STOP（理由）` にするのは、着手できる Issue が無い／週間85％以上／予算不足／止まる条件に当たった、のときだけ。inbox.md の未回答だけでは `STOP` にしない（回答待ちの Issue は飛ばして、着手できる次の Issue へ進む。回答待ちの Issue しか残っていなければ「着手できる Issue が無い」として `STOP`）。`STOP` のときも 2・3 行目は、再開したときの次のモードとモデルを書く。

## 停止時の報告（チャット、1〜3行）
inbox.md の未回答の件数（うち【相談推奨】の数）、ready にした PR の番号、保留にした Issue。それ以外は書かない。
