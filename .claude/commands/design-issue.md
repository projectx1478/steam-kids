次のIssueの設計を、役割別エージェントの議論で行う：$ARGUMENTS

あなた（メインセッション）は調整役で、自分では設計案を書かず、論点の整理と統合だけを行う。読み込みや探索はサブエージェントに任せる。

## 規則
- `git` は `--no-pager` を付ける。PowerShell で動く書き方にする。
- 設計の議論はここまで。**コードは変更しない**。ブランチも切らない。
- 決めるのは悠さん。割れた点は割れたまま出す。
- 議論の原文（`review/design/` 以下）は Issue に貼らない。コメントに残すのは要約だけ。例外として、承認済みの設計は別コメント「承認済み設計」（先頭行）として approved.md の本文を貼ってよい。観察メモ・保護者の記述は含めない。リポジトリは公開である。
- 費用を抑える：メインは大きいファイル（`style.css`、`js/ui-*.js`、`tools/validate-lessons.mjs` など）を自分で読まない。ラウンド2は意見が割れた論点だけ。

## 用語
- Issue番号が1つなら、`<G>` はその番号。複数なら、番号を `-` でつないだもの（例：`248-249-250-265-149`）。保存先は `review/design/<G>/`。
- 複数のIssueを1回で扱うときは、共通の論点（盤面の独立、規則の緩和の整合、レッスンの置き場所など）を先に議論し、そのあとIssueごとの論点に分ける。

## 手順

### 0. 事前確認
1. `git check-ignore review/design/` が該当を返すこと。返さなければ、`.gitignore` に `review/design/` が無いので、止まって報告する。
2. 各Issueについて `gh issue view <N> --json number,title,body,labels,comments` で本文を取得し、`review/design/<G>/issue.md` に、Issueごとの節に分けて保存する。
3. 前提の測り直し：Issue 本文の計測・「現状」が、Issue を書いた後にマージされた PR（`git --no-pager log --since=<Issue 作成日> origin/main`）で古くなっていないかを確かめる。古ければ、現行コードで測り直してから設計する。
4. 依存先が未完了でも、**設計の段階では止めない**。依存と実装順は、`summary.md` と `approved.md` に書く（実装するときに `/implement-issue` が確認する）。ただし、依存先が存在しない・番号が違うと思われるときは、止まって報告する。
5. `review/design/<G>/round1/` と `round2/` を作る。既存の `review/principles/` と `review/lesson-ideas/` には書かない。

### 1. 役の決定
- `--roles` があれば、それを使う。
- 無ければ、次の初期値を使い、選んだ役と理由を1行ずつ示す。表に無いIssueは、「子どもの画面・操作」「文言・報酬・戻り導線」「新しい見た目・配置」「音」「盤面・最短手数・validate」「コード」のどれに触れるかで選ぶ。議論は2役から。1役だけなら議論せず、止まって報告する。
- 複数Issueのときは、各Issueの初期値の和集合にせず、**グループ全体で最小の役の組**を提案する（各役が全Issueを読むため、役が増えると費用がかさむ）。

| Issue | 役 |
|---|---|
| 248, 249, 250, 265, 149（スイッチ群） | difficulty, impl, learner |
| 64, 251（ワープ） | difficulty, impl, screen, learner |
| 252 | difficulty, impl, learner, screen |
| 65 | difficulty, impl, learner, screen |
| 264 | difficulty, impl |
| 266, 262 | difficulty, impl, learner |
| 257 | learner, screen, impl |
| 263 | learner, guardian, screen, impl |
| 267 | learner, guardian, screen |
| 268 | sound, learner, impl |
| 269 | learner, guardian, impl |
| 242 | impl, learner, guardian |

- 役 `<role>` は `.claude/agents/design-<role>.md` に対応する。**ファイルが存在しない役は、別の役で代用せず、止まって報告する**。

### 2. 論点の整理
Issue本文を読み、設計で決めるべき論点を整理して `review/design/<G>/points.md` に書く。
- 1 Issue：3〜5個。
- 複数 Issue：共通の論点を先に（最大3個）、そのあとIssueごとに最大3個。
- 各論点に、見る役と、どのIssueの論点かを付ける。Issueの「対象外」に書かれたことは論点にしない。

### 3. ラウンド1（独立）
選んだ役のサブエージェントを**並列で**呼ぶ。各役への指示は次のとおり。
- 読むもの：`review/design/<G>/issue.md`、`points.md`、`PROJECT.md`、関連コード。
- 書くもの：`review/design/<G>/round1/<role>.md`。
- 他の役の意見は読ませない。
- 文字数の上限：1 Issueなら1200字、複数 Issueなら2000字（**この指示が各役の定義の上限より優先する**）。
全員のファイルができたことを確認する。できていない役があれば、その役だけ再実行する（1回まで）。

### 4. ラウンド2（反論）
1. `round1/*.md` を読み、役の間で意見が割れた論点、または条件が食い違った論点だけを抜き出して `review/design/<G>/round2-points.md` に書く。
2. 割れた論点が無ければ、ラウンド2は行わず、そのことを報告に書く。
3. あれば、その論点に関わる役だけを並列で呼び、他の役の `round1/*.md` を読ませて `round2/<role>.md` を書かせる（600字以内）。

### 5. 統合
コードの事実（併用規則・呼び出し順・既存の値）を決定・文案に書くときは file:行 を添える。file:行 は、その Issue の worktree（`<MAIN>/.worktrees/<N>`。origin/main 起点）で取る（main 作業ツリーの行は古いことがある。#640・#641）。レイアウトを変える決定は、4端末（360×640・844×390・768×1024・1280×800）の実寸を見本で測ってから承認に出す。

**完了見込みの案を作ってから聞く**（#370・#391・#554・#641 などで、承認の後にゲート・E2E で止まり、inbox が2〜6往復した）。悠さんに論点ごとに聞かず、全論点を決め切った案を出し、その案で Issue が完了すると言える根拠を付ける。
1. **事前点検**：`design-impl` に、次の4点を実物で確かめさせ、`review/design/<G>/precheck.md` に結果（コマンドまたは grep と、その出力の要点）を書かせる。該当しない点は「該当なし（理由）」。
   - E2E：変える id・セレクタ・文言・寸法・レッスン数を `.claude/verify/scenarios/` と `test/` で grep し、ヒットした行ごとに、新しい挙動で通るか・期待を変える必要があるかを書く。寸法の判定（`c7-board-fit` などの数値の閾値）がある行は、見本の実測値と比べる。`tools/affected-scenarios.mjs` が扱わない場所（`tools/editor` など）は、空の出力を根拠にしない。
   - validate の上限：決める文言・数値を、`tools/lib/validate/` の上限（文字数・個数・範囲）と突き合わせる。
   - 盤と検査：検査を新設・変更する設計は、`boards/` の合格盤・不合格盤を実際の validate の関数で走らせ（調整役が実行）、盤のフィールドの置き場所が既存レッスンの形と同じかを書く。
   - docs の規則：変える語・挙動を、`docs/`（`lesson-schema.md`・`learning-spec.md`・`ui-rules.md`・`gimmicks.md`）・`PROJECT.md` で grep し、文言の変更（止まる条件 c）が要る箇所を全部挙げる。
2. **案の作成**：割れた点と承認が要る点を全部決めた案を、M は2つ、L は2〜3つ考える（推奨を案A とする。#672）。割れた点が1つも無ければ1案でよい。**全項目を書く案ファイルは案A（推奨）だけ**：`review/design/<G>/plans/<案>.md` を `.claude/templates/approved.md` の形で書く（先頭の `承認:` 行は書かない）。案B 以降は `review/design/<G>/plans/<案>-outline.md` に、比較表に載せる要点（決めた内容・効果・コスト・止まりうる点・悠さんに残る確認、子どもが見る文言と規則の文言を具体値で）を 1〜2KB で書くだけにし、`check-approved.mjs`・事前ゲート・見本・盤面の実測は行わない（比較表の事前ゲート欄は「省略（案Bが選ばれたら承認後に実施）」）。案A と案B で共通の節（影響範囲・事前点検・検証計画・E2E）は `plans/common-<G>.md` に1回だけ書き、案A のファイルからは見出しと参照だけにしてよい（approved.md を書くときに展開する）。precheck.md の結果を、案A の `## 事前点検` と `## 止まりうる点と対処` に反映する。
3. **事前ゲート（案A だけ。#672）**：案A に `node tools/check-approved.mjs <案> --draft` を回し、欠けを埋めてから、`reviewer` をモード `ゲート判定` で呼ぶ（approved.md の代わりに案のファイルを渡す。渡す資料は `run-issues.md` の「ゲート判定」と同じ）。設計の直しで済む不合格は直して、もう1回だけ呼ぶ（再判定は `model: sonnet`。ゲートは合計2回まで）。**直し役（エージェント）には、ゲートの「重大」の一覧と直す節の名前だけを渡し、該当節を Edit で直させる。案ファイル全体を読み直させず、ターンの上限は20とし、超えたら直した分を報告して止める。**それでも重大が残る案は出さない（残った理由を summary.md の6に書く）。結果は `review/design/<G>/plans/<案>-gate.md` に保存する。案A が出せなければ、止まって報告する（案B を代わりに通すかは悠さんが決める）。

`review/design/<G>/summary.md` に、次の見出しで書く。
1. 合意した点
2. 割れた点（各役の立場を並べる。あなたは選ばない）
3. 悠さんの承認が要る点：**案の比較表**（案ごとに、決めた内容の要点／効果／コスト〔実装の5時間枠の％・coder の回数〕／事前ゲートの結果／止まりうる点と対処／悠さんに残る確認〔見本・実機〕）と推奨の理由1行。子どもが見るもの（見本の色・形・文言・盤面）と `.claude/`・docs の規則の文言は、案の中に具体的な値で書き、案の選択と同じ1回で聞く。案を選んだ後に聞き直す項目を残さない。
4. 設計案（共通の設計、続いてIssueごとの設計。影響範囲と検証計画つき。検証計画は「AI担当／ユーザー担当／省略」の三分）。各案の本体は `plans/<案>.md` で、ここには案の間で共通の部分と、案ごとの違いを書く。Issueごとに、次の項目を**必須**で含める（無い設計案は完成としない。入力仕様と見本は条件つき）。
   - **段の分け方**：`/implement-issue` が段ごとに新しい coder を起動する単位。段ごとに、触るファイルと関数名、変えない挙動、完了条件（`npm run verify:fast` の pass ＋その段固有の確認）を書く。**行番号は書かない**（関数名・見出しで示す）。
   - **検証コスト**：盤面・ギミックを伴う Issue は、設計案の盤面を JSON（play ステージ1つ分。`maxCommands` を含む）にして `review/design/<G>/boards/` に置き、`node tools/analyze-board.mjs --board <ファイル>` で測った最短手数・訪問状態数・別解数・所要時間を書く（調整役が実行する。出力は数行）。既存ギミックの検査条件（必須性検査・最短手数の探索など）を流用する場合は、新ギミックの向きでも成り立つか（探索の枝刈りが要らないか、検査が逆向きに効かないか）を書く。新ギミックの場合、そのギミックは未実装で `analyze-board` が扱えないので、設計時は**新ギミックのフィールドを外した盤**を測り、ギミック込みの値は段1の完了条件で測ると書く（外した盤の最短手数は、必須性検査の比較相手になる）。`tools/validate-lessons.mjs`（検査本体は `tools/lib/validate/` に分割済み）の検査を新設・変更する場合は、検査ごとに**合格する盤と不合格になる盤**を1つずつ `boards/` に置き、どちらになるかと理由を書く。片方が作れない検査は、常に真か常に偽なので、文言を直してから設計案を完成とする。盤面を伴わない Issue は「対象外」と理由を書く。実行時間を測る設計（検証コストに秒数を書くもの）は、**許容増分**を次の式で書く：generate 段は main 比 ≤1.25、合計は main 比 ≤1.15（main と交互に各3回測った中央値の比）。これは**仮置き**で、最初の3回の利用後に見直す（見直しは別 PR・`.claude/` の対話変更）。式を超える設計は、超える理由を書いて悠さんの承認項目に入れる。
   - **使う共通部品／新しく作る理由**：必須。`docs/components.md` の部品の一覧を読み、この設計が使う部品（名前と置き場）を書く。一覧に同じ役の部品があるのに自前で組む場合は、その理由を書く。新しい部品を作る場合は、既存の部品で足りない理由を書く。画面・演出・検査を変えない Issue は「該当なし」と1行書く。
   - **部品化の置き換え計画**：部品化（共通部品の新設、または既存の自前実装の置き換え）の Issue は必須。次の3つを書く。(1) 置き換え対象の一覧（ファイル・関数・件数。`grep` の結果）、(2) PR の分け方（1 PR にまとめるか、段・PR を分けるか、分ける理由）、(3) 禁止へ移る条件（`test/forbidden-registry.mjs` の登録表と `test/forbidden-baseline.json` の基準をいつ・どう変えるか。基準を上げる変更は悠さんの承認項目）。部品化でない Issue は「該当なし」と1行書く。
   - **入力仕様**：設計が盤面JSON・レッスンJSON・ギミックの入力（フィールド）を新設または変更するときは必須。無い設計は「該当なし」と1行書く。内容は手順6の `決定` の「入力仕様」と同じ。調整役は、この入力仕様だけで `impl-coder` が段の最初（新設なら段1-1）を推測なしで書けるかを確かめる（フィールドごとに、名前・形・範囲・省略時の値・式・受け付けない値が埋まっているか。埋まっていなければ設計案を完成としない）。
   - **見本**：色・形・記号・文言・盤面の見た目を新設または変更するときは必須。無い設計は「該当なし」と1行書く。360px 幅の静止画を `review/design/<G>/mock/` に置き、承認前に悠さんに見せる（リポジトリのコードは変えない）。見本の作成は、`analyze-board`・`verify:fast` などの測定と並行させない。静止画の承認は実機確認の代わりにならないので、7にも書く。
   - **状態遷移表**：画面遷移・履歴・端末の戻る・ダイアログ・ボタンの無効化を変えるときは必須。design-impl が書いた表（起点の状態×操作〔連打・端末の戻る・ブラウザの進む・実行アニメ中を含む〕→起きること・行き先・文言）を転記する。変えない設計は「該当なし」と1行書く。
   - **文言の経路一覧**：子どもが見る文言を新設・変更するときは必須。その文言が出る経路（ボタン・端末の戻る・進むなど）ごとに、出る条件・行き先・文言を表にする。行き先が違う経路に同じ文言を使うときは理由を書く。悠さんへは一覧ごと1回で聞く。無い設計は「該当なし」と1行書く。
   - **E2E の追従**：`E2E への影響` に挙げたシナリオごとに、新しい挙動を通るために足す手順（押すボタン・待つ要素・足す check）を書く。
5. 実装順と依存（複数Issueのとき必須。`/implement-issue` を回す順番と、その理由）
6. 未検証の記述（研究・他ゲームへの言及、静止画からの想像、実行していない最短手数の数値）
7. 悠さんが実機で確認すること（操作感・音・子どもの反応）

チャットには、3の比較表と推奨、5・7の要点と `summary.md` のパスを出して、**停止**する。悠さんが案を選ぶ（部分的な変更の指示があれば、それも受ける）。

### 6. 承認後（悠さんの返事を受けたら）
0. 選ばれた案の `plans/<案>.md` を写して approved.md の元にする。悠さんの返事に案と違う指示があれば、その指示に関わる節を**全部書き直す**（末尾や節の途中に追記しない。追記で本文と食い違い、未決が残った：#391・#397・#389・#468・#497）。書き直した節が precheck.md の4点に関わるなら、その点だけ事前点検をやり直す。最後に `node tools/check-approved.mjs <approved.md>` を回す（「未決」「要確認」や雛形の `<…>` が残っていれば欠けになる）。
1. 返事に書かれた決定を、**Issueごとに** `review/design/<N>/approved.md` にまとめる。複数Issueのときは、共通の決定と、そのIssueの設計を、どのファイルにも含める（`/implement-issue` は `review/design/<N>/approved.md` だけを読むため）。先頭行は `承認: 悠 <日付>` にする。**この行は、悠さんが決定を明示した返事を受けたときだけ書く**。内容は次の節で書く。`/implement-issue <N>` の一行だけで進められるよう、実装に必要な指示は、チャットではなく approved.md に必ず含める。approved.md は `.claude/templates/approved.md` から書く。節名は、`/implement-issue` が読む4節（`決定`・`段の分け方`・`実装時に守ること`・`E2E への影響`）に加え、`tools/check-approved.mjs` が前方一致で確かめる節（`検証コスト`・`検証計画`・`使う共通部品`・`部品化の置き換え計画`・`入力仕様`・`状態遷移表`・`文言の経路一覧`・`事前点検`・`止まりうる点と対処`）の見出し（`## ` で始める）を使う。
   - `決定`：確定した設計案、割れた点の決定。先頭に**経路**を1行書く（`/implement-issue` で進める、または停止して別経路〔`/implement-issue-light`・設計のやり直し・悠さんの手作業など〕。その理由つき）。
     - **入力仕様**：設計が盤面JSON・レッスンJSON・ギミックの入力（フィールド）を新設または変更するときは必ず書く。無い設計は「入力仕様：該当なし」と1行書く。書くこと：フィールド名と形（例を1つ）／値の範囲／省略時・初期値（周期なら初期位相）／判定や数え方の式（例：手番の数え方）／他の要素との重なり・併用の禁止／受け付けないフィールド・値（廃止したフィールドを含む）と、指定されたときの validate の扱い／それを検査する場所（`tools/lib/validate/` 内のどの検査か。入口は `tools/validate-lessons.mjs`）。既存ギミック（`docs/gimmicks.md` の keys・switches など各節の「JSONフィールド」）の入力形（`spec.<フィールド名>`・省略時の既定値・座標は `{x, y}`）に合わせ、違う形にするときは理由を書く。summary.md の「設計案」の入力仕様から転記する（無ければ approved.md を書かず、補ってから悠さんに確認する）。
   - `段の分け方`：summary.md の「設計案」から必須項目として転記する（無ければ approved.md を書かず、補ってから悠さんに確認する）。各段の**完了条件**に、検証コマンドと、その段が生成テスト（generate）を含むか含まないかの区別を書く。
   - `実装時に守ること`：次の5項を必ず含める。
     - 範囲：触るファイル／触らないファイル。触らないものに、`.claude/`、`PROJECT.md`、`CLAUDE.md`、`AGENTS.md`、`.claude/verify/config.mjs`、凍結fixture（cmd-01・donguri-01）を明記する（設計で触る場合は、その理由と範囲）。ファイルやモジュールを足すときの `APP_SHELL` の更新は、触らないものに含めず、更新してよいと書く。`APP_VERSION`・`CACHE_NAME` は触らない（自動付与。値を変えると CI が失敗する）。
     - 停止条件：探索の状態数が `verify:fast` の枠（`tools/verify-fast.mjs` の `TOTAL_MS`）を超える、同じ失敗が2回続く、承認範囲外の変更が必要になる、など。設計に固有のものを書く（`implement-issue.md` の停止の規則と重ねて書かない）。
     - 報告：`implement-issue.md` の「報告して停止」の標準に対する、そのIssue固有の上乗せだけを書く（例：差分の全文、`git --no-pager diff --numstat`）。無ければ「標準どおり」と書く。
     - PR規則：`implement-issue.md` の「規則」（マージしない）、「コミットの準備」（作成者は noreply 形式）、「push と PR」（`Closes #<N>`・本文の書き方）の標準に対する、そのIssue固有の上乗せだけを書く。無ければ「標準どおり」と書く。
     - 事前許可：先例があり、実装中に止まらずに行ってよい変更。項目ごとに、変更の内容／先例（Issue・PR番号）／範囲（ファイル・関数・値）を書く（例：レッスンを足したときに落ちる全ステージ回帰テストの期待値を、足したレッスンの分だけ更新する）。範囲を超える変更、規則の「触らないもの」に当たる変更は書かない。無ければ「なし」と書く。
     - 上の「報告」「PR規則」は調整役（メイン）の担当。`impl-coder` は読み飛ばしてよい。
   - `E2E への影響`：従来どおり。summary.md の「E2E の追従」（シナリオごとに足す手順）も転記する。
   - `状態遷移表`・`文言の経路一覧`：summary.md から転記する（該当なしの1行も転記する）。
   - `見積もり:`：1行で、実装の5時間枠の％と coder の呼び出し回数（段の数＋修正枠。L は2、M は1）を書く。
   - `検証コスト`：summary.md から必須項目として転記する（無ければ approved.md を書かず、補ってから悠さんに確認する）。各値に「実測（コマンドと日付）」か「未測定（定義・コードから導いた推定）」かを付ける。導いただけの値を実測と書かない。許容増分（generate 段 main 比 ≤1.25、合計 main 比 ≤1.15。仮置き・最初の3回の利用後に見直す）も、summary.md の書き方のまま転記する。
   - `使う共通部品／新しく作る理由`、`部品化の置き換え計画`：summary.md から必須項目として転記する（該当なしの1行も転記する。無ければ approved.md を書かず、補ってから悠さんに確認する）。
   - `検証計画`、`実装順と依存`：従来どおり。
   - `事前点検`：precheck.md の4点（E2E・validate の上限・盤と検査・docs の規則）の結果の要点。
   - `止まりうる点と対処`：実装・CI で止まりうる点ごとに、起きたときの対処を書く。先例と範囲が書ける対処は `実装時に守ること` の事前許可にも入れ、実装中に inbox へ戻らないようにする。対処を決められない点は、案の比較表で悠さんに聞いておく。
1b. approved.md が承認済みになったら、Issue に転記する。`gh issue comment <N> --body-file <一時ファイル>` で、先頭行を `承認済み設計` にし、続けて approved.md の本文（先頭の `承認:` 行を除く）を貼る。観察メモ・保護者の記述は含めない。`review/design/` 以下の議論の原文は貼らない。
2. 各Issueに要約コメントを投稿する（`gh issue comment`）。内容は、決定事項と検証計画だけ。議論の原文は貼らない。承認済み設計の転記は手順 1b（別コメント・上の例外）で行う。承認済み設計のコメントが複数あるときは最新のコメントが正本。
3. 「`/clear` のあと `/implement-issue <N>` で、実装順に進める」と報告して、停止する。
